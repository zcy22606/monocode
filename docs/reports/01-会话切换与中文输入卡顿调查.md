## 已复现：旧草稿覆盖正在输入的内容

关键位置：

- `src/features/sessions/ui/SessionPane.tsx:702`：每次父组件渲染，把 `draftRef.current` 再作为 `initialDraft` 传入。
- `src/features/sessions/ui/Composer.tsx:908`：`initialDraft` 变化后，只要与 DOM 值不同就执行 `el.value = initialDraft`，没有检查组合输入状态。
- `src/features/sessions/ui/Composer.tsx:934`：子组件在 effect 中调用 `onDraftChange(draft)`，把本地输入反馈给父组件的 ref。
- `src/features/sessions/ui/Composer.tsx:2160` 附近：输入事件更新本地 `draft`；textarea 没有 `compositionstart` / `compositionend` 状态跟踪。

问题不是单纯的受控 textarea。这里虽然固定了 `defaultValue`，仍保留另一条 effect 回写 DOM 的通道。

实际探针采用与 SessionPane 一样的“父组件 ref 保存草稿，子组件 effect 通知”的结构，并使用真实 Composer 组件：

1. 输入已提交的 `你好`，父组件 ref 更新为 `你好`；父组件自身尚未因输入重新渲染。
2. 在同一批更新中触发父组件刷新和组合输入事件，DOM 已变成 `你好shi`，输入事件携带 `isComposing: true`。
3. 父组件渲染时读到上一份 ref：`你好`。Composer 的回写 effect 把 DOM 改回 `你好`。
4. 子组件的草稿 effect 又把缓存更新成 `你好shi`。此时 **DOM 与缓存不同步**。
5. 下一次父组件刷新，把 `你好shi` 作为字符串写回 textarea。

探针输出：

```json
{"case":"overlapping-parent-refresh","dom":"你好","cachedDraft":"你好shi"}
{"case":"next-parent-refresh","dom":"你好shi","cachedDraft":"你好shi"}
```

对照场景：先完成输入更新，再让父组件回传与 DOM 相同的值，内容保留，`defaultValue` 也保持挂载时的值。这说明既有 `Composer.ime.test.ts` 覆盖的情况正常，但没有覆盖父子更新交错。

这里的确定事实是**应用在组合输入期间写入旧值，并随后恢复拼音字符串**。候选窗具体如何终止必须由原生 WebKit + 微信输入法验证，不能用合成 CompositionEvent 代替。

### 建议的修复边界

- 本地编辑中的 textarea 保持输入所有权。`initialDraft` 只负责初始化；外部恢复、引用、清空等应有明确请求身份，避免把普通父组件刷新误当作外部编辑命令。
- 组合输入期间推迟外部 `.value`、选区和强制焦点变更，组合完成后再按请求版本决定是否应用。
- 不能只增加 `isComposing` 早退：还要处理旧请求在 `compositionend` 后覆盖新输入的情况。
- 保留会话切换草稿、粘贴、引用、Esc 恢复、↑/↓ 历史、提问表单等行为；不为修输入而取消正常草稿保存。

依据：[W3C UI Events](https://www.w3.org/TR/uievents/) 描述了组合输入过程及伴随的 DOM/input 更新；[React useEffect](https://react.dev/reference/react/useEffect) 说明 effect 与渲染、交互的执行关系。这些文档解释事件模型，实际缺陷证据来自本仓库探针。

### 已确认的更新路径

`src/app/model/harnessFlush.ts` 已经按前台约 30 ms、后台 500 ms 合并事件。`src/app/App.tsx:1619` 的队列消费仍更新顶层 `sessions`，带动 App 执行以及当前会话 pane / Composer 更新。持续输出会增加上述草稿交错的机会，也会与输入和点击竞争主线程时间。

已有优化也真实存在：

- `PaneTree.tsx` 对一直隐藏的树跳过渲染。
- `AgentTranscript.tsx` 对一直隐藏的转录跳过更新。
- `TranscriptTurnCache` 复用未变的历史轮次。
- `persistFingerprint` 使用 block 身份，已不是每次比较就序列化整段历史。

因此不能把问题笼统描述为“所有隐藏会话每个 token 都重新渲染”或“每个 token 都全量 JSON.stringify”。后续应测量每批事件应用、顶层派生数据、当前轮次渲染、布局和文件索引更新各自的成本。

输入事件中的 `resizeComposer` 会同步读取布局并修改高度，属于需要测量的放大因素；目前没有证据证明它是主瓶颈。文件目录更新还会刷新文件索引并让各 Composer 构建引用索引，这也是候选路径，尚未与本次采样的匿名 JIT 帧对应起来。

## 补充调查（Claude，2026-10-16 04:00–04:50）

用 `sample`（10 秒，用户正在用输入法打字）和 Instruments Time Profiler（`xcrun xctrace record --template 'Time Profiler' --attach <WebContent pid>`，导出带时间戳的样本后按主线程连续忙碌段统计）补齐了上文缺的归因。xctrace 不需要 Safari Web Inspector，以后排查卡顿优先用它。

### 「点两下」

- 窗口没在前台时，第一下点击只用来激活窗口：`tauri.conf.json` 没开 `acceptFirstMouse`，WKWebView 默认不把激活点击交给页面。这是确定的机制，是否就是用户遇到的情况待用户确认（是不是从别的应用切回来时才这样）。
- 窗口在前台时：#1 的约 1 秒长任务（回到窗口的那一刻也会来一次）和 #3 之后变慢的那段时间，第一下点击要等很久才有反应，看起来像没点上。

### 中文输入

#1、#2、#4 都是在用户打字时把主线程堵住几十毫秒到一秒以上；输入法组词期间 WebContent 跟不上，组词状态和页面就会对不上。上文复现的草稿回写竞态需要父组件刷新和输入事件落在同一批更新里；真实浏览器里输入事件的同步渲染和 effect 在同一个事件监听器内就跑完了，这个窗口是否真的存在尚未证实，先按次要原因处理。

### 已做的修复（分支 `perf/sol-82`，工作树 `../monocode-worktrees/perf-sol-82`，未提交）

1. `fileIndex.ts`：重扫结果和上次一样（路径和类型逐项相同）时沿用原数组、不通知订阅者。invalidate 之后也能比较（单独记最近的列表，上限 16 个目录）。
2. `fileMentions.ts` + `Composer.tsx`：`sharedMentionIndex(files, extras)` 按「文件列表数组 + 附加项（笔记、关联对象）」缓存索引，同一目录的输入框共用一份。openroboto 根目录真有文件增删时从 23 次构建降到 4 次（3 个带关联的会话各自一份）。
3. `soloyard/data/api.ts`：一次刷新里相同的请求只发一个；结果和上次一样就沿用原对象，组件函数都不跑。
4. `App.tsx`：快捷键录制判断改成看 `document.activeElement`（录制框只在获得焦点时录制，失焦就停）。
