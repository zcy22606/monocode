# 项目工作流：头脑风暴 → 立项 → 功能定下来

和用户逐条定下来的（2026-10-09 ~ 10-12）。范围：从一个想法开始，到第一个迭代的范围定好、点「开始」为止；之后是建造期（Issues、迭代、开工、验收）。

## 分工

- **用户**：拍板（尤其是单向门）、做减法（在迭代页挪功能）、点关口按钮。
- **agent**：调研、思考、写东西，并且一直维护项目的 overview。
- **应用**：不自己调模型。它负责存储、显示、推导阶段、在关口给会话发提示词。

## 阶段

大的期：**想法 → 立项 → 建造 → 上线**，另有两个终止态：**搁置**、**放弃**（要写原因）。

- **想法**：只存在于头脑风暴里，是一条隐藏的「想法项目」，不进项目列表。
- **立项**：头脑风暴「提升为项目」后进入。立项期的小步从数据推出来，不用手动点：
  - 待立项：还没有立项卡；
  - 待拍板：有单向门没定；
  - 待排版本：还没有迭代；
  - 待减法：有迭代，但一个都没开始。
- **建造**：有迭代开始过。直接添加文件夹建的老项目跳过立项，从这里开始。
- 只有这几个要手动标：搁置、放弃、上线。
- MCP 的 `get_project` 返回「阶段 + 下一步」；概览页显示同样的内容。

## 流程

| 步 | 在哪 | agent | 用户 | 产出 | 关口 |
|---|---|---|---|---|---|
| 1 头脑风暴 | 侧栏「头脑风暴」 | 聊三件事：给谁用、现在怎么凑合、为什么会换。从第一句起维护想法项目的中文标题、英文名（将来的文件夹名）、一句话描述和 overview；推不出来就先叫「未命名想法」，方向变了就更新 | 聊 | 想法项目、overview、工作文件夹里的文档 | — |
| 2 轻验证（可选） | 同一个会话 | 先问用户要不要查，再查竞品和用户声音；证据记进证据表（有编号），结论写进 overview | 决定查不查 | 证据、overview | — |
| 3 提升 | 头脑风暴页「提升为项目」 | — | 在弹窗里确认或修改预填的标题、英文名、描述、issue 前缀 | 项目文件夹（英文名）、正式项目（出现在项目列表）、阶段变成立项 | **点「提升」= 决定立项**；不要的想法归档成「放弃」 |
| 4 立项盘点 | 应用自动给会话发提示词 | 盘点已有的东西（overview、证据、决策、`docs/`），列立项覆盖表：每一块标「已有够用 / 有但要补 / 没有」并附证据编号，再给出预计耗时 | **看覆盖表，点头再跑** | 覆盖表（在对话里） | 用户点头 |
| 5 立项（只补缺） | 会话 | product-thinking 的「立项」只跑缺的和不够的，已有的直接引用；默认接着跑加法的「列全」 | 等 | 完整立项卡、功能全集写进 `docs/`；结论更新进 overview；单向门决策进 Decisions 页；功能进「待定」 | — |
| 6 拍板 | Decisions 页 | 不代做决定（用户在对话里说的决定，可以代为写进应用） | 定单向门：首要人群、目标市场等；双向门可以一键全部采纳 | 决策 | **单向门没定，下一步不开跑** |
| 7 排版本表 | 会话 | 加法的「版本表」，导入后迭代页出现 v0.1 / v1.0 / … | 等 | 迭代表 | — |
| 8 减法 | 迭代页 | — | 挪功能，标「不做」「另立项」 | 迭代表 | — |
| 9 减法审查 | 会话 | 审查挪完的版本表：有没有减过头、减不够，每个版本的工作量；有问题就提成新决策 | 看审查，按需再挪 | 版本表审查（`docs/`）、新决策 | **「开始」第一个迭代 = 立项结束，进入建造期** |

深挖、商业、技术、PRD 这四个命令都可选，不卡流程，在概览页作为「建议做」列出来。

## overview：项目的产品说明书

相当于项目的 CLAUDE.md，但只讲「做什么、为什么」，不放技术和技术规范。从头脑风暴第一句起就有，agent 根据头脑风暴和之后的对话一直更新。

- **结构化字段**：中文标题、英文名、一句话描述、阶段、止损线。
- **正文分节**：
  - 背景与问题
  - 目标用户
  - 现有替代和竞品
  - 调研发现
  - 关键决策
  - 范围和不做的
  - 成功指标
  - 风险与待验证假设
  - 还没想清楚的
- **更新**：agent 一次只改一节，不整篇重写。正文里只引用决策和证据的编号（D-x / E-x），不抄内容；显示时按决策表的实时状态渲染。
- **用户改了怎么办**：用户可以直接改任何一节。agent 改某一节前，如果发现用户在它上次读过之后改过这一节，就不覆盖，改成在对话里提建议。
- **给 agent 读**：
  - 系统提示词里只自动带一个短摘要：一句话描述、阶段、已定的关键决策标题。
  - 全文需要时经 MCP 读。
- **谁来更新**：
  - 头脑风暴、立项相关的会话一定要更新；
  - 普通写代码的会话只在用户做了产品层面的决定时才更新，技术决定不进 overview。
- **立项卡和 overview**：立项卡是完整报告，放 `docs/`；overview 永远是精简后的「当前真相」。

## 存储（以谁为准）

| 东西 | 存哪 | 说明 |
|---|---|---|
| overview（字段 + 分节） | 数据库 | 每次变动另写一份只读快照 `docs/overview.md`，进 git，也给没接 MCP 的 agent 读 |
| 决策、证据 | 数据库 | product-thinking 的 `decisions.json` / `evidence.json` 只是它自己用的工作副本，命令开始和结束时经 MCP 同步，以应用为准 |
| 文档（立项卡、功能全集、调研报告、想法卡…） | 项目文件夹 `docs/`，进 git | Docs 页直接读文件渲染：`.md` 按 markdown 显示，product-thinking 的 `.json` 用块渲染器显示；数据库不存文档正文。头脑风暴期的文档在工作文件夹里，提升时随文件夹挪进项目 |

## 提升为项目

1. 弹窗预填 agent 最新维护的中文标题、英文名（文件夹名，必填，校验能不能当文件夹名、目标位置有没有重名）、一句话描述、issue 前缀（按英文名生成），都可以改。
2. 确认后：建项目文件夹 → 会话挪过去 → 工作文件夹里的文档挪进项目的 `docs/`，其余文件挪进 `brainstorm/` → 想法项目转成正式项目，阶段改成立项，出现在项目列表。
3. 自动给会话发提示词：告诉 agent 已经提升为项目（名称、路径、前缀），让它按最新上下文更新 overview，然后进入立项盘点（流程第 4 步）。

## 要改的地方（对应 SOL 的 issue）

- **SOL-71 阶段**：推导规则；手动标搁置 / 放弃（写原因）/ 上线；MCP 返回阶段和下一步。
- **SOL-70 overview**：分节存储、MCP 读写、冲突规则、快照文件、系统提示词带短摘要、概览页。
- **SOL-11 想法项目和提升**：头脑风暴即建想法项目；agent 维护标题 / 英文名 / 描述；提升弹窗；提升后发提示词；项目设置页能手动改这些字段。
- **SOL-12 Decisions 页**：拍板单向门、批量采纳双向门；MCP 读写决策和证据。
- **SOL-13 Docs 页**：读项目 `docs/` 里的文件渲染；数据库不再存文档正文。
- **立项增量模式**：改 product-thinking 技能（`~/Playground/产品方法论/product-thinking`）：先盘点、出覆盖表、点头再跑、只补缺；决策和证据走 MCP；文档写进 `docs/`；结束后更新 overview。
- **SOL-57 头脑风暴后续**：归档 = 想法项目标「放弃」或「搁置」；提升后的文档在 Docs 页可见。
